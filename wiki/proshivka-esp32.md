Как собирать и заливать прошивки ESP32 из командной строки, без Arduino IDE и без
кнопки BOOT. Проверено на двух машинах проекта (Windows 11, платы ESP32 DevKit 30pin
с USB-UART CH340). Здесь же — расследование случая, когда на одной из машин
автосброс не срабатывает.

## Команды

```
arduino-cli board list
arduino-cli compile -b esp32:esp32:esp32 --build-path <скетч>\build <скетч>
arduino-cli upload  -b esp32:esp32:esp32 -p COM6 --input-dir <скетч>\build <скетч>
```

`--build-path` и `--input-dir` парные: upload берёт готовую сборку и не компилирует
заново. Признак успеха — строки `Hash of data verified.` и `Hard resetting via RTS pin...`.

Порт смотреть перед каждой заливкой: при передёргивании USB номер меняется
(на второй машине скакал COM6 ↔ COM4).

## Что arduino-cli делает под капотом

Ядро esp32 3.3.x зовёт не esptool напрямую, а обёртку `flasher.exe` из ядра:

```
flasher.exe --esptool <Arduino15>\packages\esp32\tools\esptool_py\5.3.1\esptool.exe
  --chip esp32 --port COM6 --baud 921600 --before default-reset --after hard-reset
  write-flash -z --flash-mode keep --flash-freq keep --flash-size keep
  0x1000 bootloader.bin 0x8000 partitions.bin 0xe000 boot_app0.bin 0x10000 <скетч>.bin
```

Ключи через дефис (`default-reset`) — синтаксис esptool 5.x; в 4.x было
`default_reset`. Скорость 921600 — штатная, снижать не пришлось.

## Если заливка просит BOOT

Порядок проверки по частоте причин:

1. **Порт занят.** Вкладка браузера с Web Serial (страница-пульт!) держит порт и
   рвёт заливку молча. Также Arduino IDE, Serial Monitor, PlatformIO, свой скрипт
   чтения. Признак: `Access to the port is denied` либо тишина.
2. **Порт сменил номер** — `Could not find file 'COM6'`. Смотреть `board list`.
3. **Скорость**: `--board-options UploadSpeed=115200`.
4. **Питание/порт**: другой USB-порт (2.0 вместо 3.0 или наоборот), напрямую в
   материнку, либо, как ни странно, через дешёвый USB 2.0 хаб — он нормализует
   фронты DTR/RTS.
5. **Что-то висит на GPIO0/2/12/15** — датчик или провод на служебном пине
   меняет режим загрузки. Проверять на голой плате.

## Расследование: та же плата шьётся на машине 2 и не шьётся на машине 1

Симптом на машине 1: `Wrong boot mode detected (0x13)` — сброс по RTS→EN проходит,
плата перезагружается, но GPIO0 не притягивается, чип стартует в обычном режиме.
Помогает только удержание BOOT. Перебраны: кабели, порты, esptool 4.9 и 5.1,
задержки сброса, все полярности DTR/RTS.

Что совпало на обеих машинах (сентябрь 2026), то есть НЕ является причиной:

| | Машина 2 (шьётся) | Машина 1 (не шьётся) |
|---|---|---|
| Драйвер CH340 | wch.cn 3.9.2024.9, 16.09.2024, oem51.inf | wch.cn 3.9.2024.9, 16.09.2024 |
| Чип | CH340, VID_1A86 PID_7523 | тот же (плата одна и та же) |
| Windows | 11, сборка 26200 | 11 |
| Device Parameters порта | PollingPeriod=0, EnumerationRetryCount=0 | ? |

Что различается и что проверять дальше:

* esptool **5.3.1** против 4.9/5.1 — первым делом взять бинарник с машины 2 или
  обновить ядро: `arduino-cli core upgrade esp32:esp32`.
* USB-порт: на машине 2 — USB 3.0 root hub, Intel USB 3.10 xHCI, напрямую.
* Штатная настройка последовательности сброса esptool 5:
  `ESPTOOL_CUSTOM_RESET_SEQUENCE=D0|R1|W0.1|D1|R0|W0.5|D0` (D — DTR, R — RTS,
  W — пауза в секундах); `--trace` показывает, что реально дёргается.
* Решающий тест с тестером: открыть порт из PowerShell, выставить
  `RtsEnable=false; DtrEnable=true` и померить GPIO0. Если на машине 1 при DTR=true
  на GPIO0 остаётся 3.3 В — фронты формирует хост, лечится портом/хабом, не софтом.

Статус вопроса: открыт. Машина 1 шьёт с удержанием BOOT.

## Чтение Serial без Arduino IDE

PowerShell, без установки чего-либо:

```powershell
$p = New-Object System.IO.Ports.SerialPort('COM6', 460800)
$p.DtrEnable = $false; $p.RtsEnable = $false   # не держать плату в ресете
$p.ReadTimeout = 500; $p.Open()
1..20 | % { try { $p.ReadLine() } catch {} }
$p.Close()
```

Сброс платы программно: `RtsEnable = $true`, пауза 100 мс, `RtsEnable = $false` —
так ловится стартовый отчёт прошивки.
